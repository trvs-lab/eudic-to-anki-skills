# Eudic-to-Anki 日期范围导出与限频保护规格

日期：2026-08-10

状态：已实施

## Problem Statement

当学习者要求导出「过去一周」「最近 7 天」或一个明确的连续日期范围时，`eudic-to-anki` agent 可能把范围展开成多个单日任务，并同时启动多个欧路导出进程。一次导出并不等于一次 HTTP 请求：导出器会先查询生词本分类，再逐分类分页读取单词，最后在本地按日期过滤。多个单日进程会重复执行整套分类和分页请求，短时间内将请求量放大到原来的数倍，触发欧路 API 限频。

当前日期范围工作流已经给出单次区间导出命令，但主 Skill 没有明确要求 agent 按请求类型选择对应工作流。主执行示例和 Export 模块仍以单日占位符及 `_day_...` 工件命名为主，容易让 agent 把连续日期范围理解成若干个独立日期。导出脚本本身支持 `--start-date` 与 `--end-date`，不会主动按天拆分，但缺少跨进程互斥和请求节流，因此无法阻止错误执行计划形成请求突发。

该问题会使正常的周度导出在取得任何可用结果前失败。限频发生后，学习者还需要等待服务恢复，无法继续生成卡片。现有错误信息也没有提供本次导出的分类请求数、分页请求数和总请求数，难以判断是认证问题、单次数据量过大，还是多个导出进程并发造成。

## Solution

把「一次连续日期范围只执行一次欧路导出」设为 `eudic-to-anki` 的强制工作流规则。agent 在执行前先按请求类型选择工作流：单日或「昨天」进入单日工作流；连续日期范围、「过去一周」或「最近 N 天」进入日期范围工作流；指定词表进入词表工作流。日期范围必须先解析为一个闭区间，再使用一条同时包含开始日期和结束日期的导出命令。不得按天拆分，也不得并行启动多个导出进程。

导出器增加两项执行保护。第一项是本机非阻塞单实例锁：进程必须在首次网络请求前取得固定导出锁；已有导出运行时，新的进程在发出任何欧路请求前直接终止，并提示改用一条日期范围命令，不排队等待，也不自动重试。第二项是统一请求节流：分类请求、单词分页请求和允许的限频重试都经过同一个节流器，默认最多每分钟 25 次请求，即相邻请求开始时间至少间隔 2.4 秒。

导出器区分限频与认证失败。`429` 视为限频；`403` 只有在响应正文明确表示访问频率过高时才视为限频，其他 `403` 继续按认证或权限错误处理。仅当限频响应提供有效且不超过 120 秒的 `Retry-After` 时，等待指定时间并对当前请求重试一次；没有等待信息、等待时间无效、等待时间过长或重试仍失败时立即终止整次导出。失败后不得继续请求后续分类或分页，也不得生成看似完整的部分导出文件。

导出成功或失败时输出不含敏感信息的请求统计，包括分类请求数、单词分页请求数、重试请求数和总请求数。这样可以在不暴露欧路 token 的前提下判断请求来源。日期过滤、遇见元数据、输出格式及下游制卡流程保持不变。

## User Stories

1. 作为按周整理生词的学习者，希望「过去一周」只触发一次欧路导出，以便避免重复查询相同分类和分页数据。
2. 作为指定明确开始日期与结束日期的学习者，希望 agent 使用一条区间命令，以便一次取得完整范围内的生词。
3. 作为导出「最近 N 天」生词的学习者，希望相对日期先被解析为一个闭区间，以便日期边界明确且可复查。
4. 作为只导出某一天生词的学习者，希望开始日期与结束日期可以相同，以便继续支持现有单日流程。
5. 作为使用自然语言发起任务的学习者，希望 agent 自动选择正确的日期范围工作流，以便不需要了解底层命令参数。
6. 作为担心欧路访问限制的学习者，希望连续日期范围禁止按天拆分，以便请求数量不随范围天数成倍增长。
7. 作为担心并发请求的学习者，希望多个欧路导出进程不能同时运行，以便一次错误规划不会形成请求突发。
8. 作为重复点击或重复发起任务的学习者，希望第二个导出在发出 HTTP 请求前停止，以便不会消耗额外配额。
9. 作为收到并发阻止提示的学习者，希望错误信息明确说明已有导出正在运行，并提示使用单次日期范围命令，以便能够正确重试。
10. 作为等待当前导出完成的学习者，希望导出锁在成功、失败或异常退出后释放，以便后续正常任务不会永久被阻止。
11. 作为使用全部生词本分类的学习者，希望分类查询和逐分类分页仍然完整执行，以便不会为了减少请求而漏掉词条。
12. 作为导出大量生词的学习者，希望所有欧路 API 请求受到统一节流，以便单个进程也不会在短时间内超过访问限制。
13. 作为排查访问限制的维护者，希望分类请求、分页请求和重试请求使用同一个计数口径，以便准确理解总请求量。
14. 作为遇到 `429` 的学习者，希望导出器能够识别限频响应，以便给出与认证失败不同的处理结果。
15. 作为遇到 `403` 的学习者，希望只有明确表示访问频率过高的响应才按限频处理，以便无效 token 或权限问题不会被错误重试。
16. 作为收到 `Retry-After` 的学习者，希望当前请求最多等待并重试一次，以便服务明确允许恢复时能够继续导出。
17. 作为遇到没有等待信息的限频错误的学习者，希望整次导出立即停止，以便脚本不会猜测等待时间并继续消耗配额。
18. 作为遇到持续限频的学习者，希望第二次请求失败后停止所有后续分页和分类请求，以便限制错误不会进一步扩大。
19. 作为依赖完整导出文件的学习者，希望失败时不生成看似成功的部分 CSV 或 JSON，以便下游不会误导入不完整数据。
20. 作为排查周度导出问题的维护者，希望结果中显示请求统计，以便区分数据量、分页数量和错误并发造成的问题。
21. 作为关注凭据安全的学习者，希望请求统计和错误信息不包含欧路 token 或完整认证头，以便日志可以安全查看。
22. 作为依赖本地日期的学习者，希望节流与单实例保护不改变日期解析和本地时区过滤，以便导出范围仍符合实际阅读日期。
23. 作为依赖来源例句和遇见记录的学习者，希望导出保护不改变 `category_id`、`category_name`、`add_time_utc`、`add_time_local` 和 `context_line`，以便下游语境锚点卡继续获得完整元数据。
24. 作为继续使用后续制卡流程的学习者，希望区间导出的文件仍能直接进入占位生成、coach 合并、校验和 Anki 预演，以便修复不引入新的人工步骤。
25. 作为维护 Skill 规则的开发者，希望主 Skill、日期工作流、Export 模块和命令规则示例采用同一日期范围表达，以便 agent 不会从不同文档得到冲突指令。
26. 作为验证 Skill 行为的开发者，希望「导出过去一周」的验收结果只包含一个 `eudic_export.py` 调用，以便未来文档调整不会恢复逐日并发行为。
27. 作为验证导出器的开发者，希望并发和节流测试使用假 HTTP 边界及假时钟，以便测试快速、确定且不访问真实欧路服务。
28. 作为运行日常导出的学习者，希望正常单次区间导出不需要新增命令参数，以便现有使用方式保持简单。

## Implementation Decisions

- 主 Skill 增加强制工作流路由。单日或「昨天」读取单日工作流；连续日期范围、「过去一周」或「最近 N 天」读取日期范围工作流；指定词表读取词表工作流。agent 必须在执行任何导出命令前完成路由。
- 主 Skill 不再维护容易与子工作流漂移的单日完整命令链。主入口只描述公共阶段和路由规则，具体工件命名与命令由被选中的工作流负责。
- 连续日期范围的产品级不变量为：一次用户导出请求对应一次 `eudic_export.py` 调用。不得为范围内每一天分别调用，不得通过子任务、子 agent 或并行 shell 命令同时运行多个导出。
- 日期范围先在系统本地时区解析为闭区间。区间导出同时传入开始日期与结束日期，输出使用包含两个日期的 `_range_` 标识。单日流程允许开始日期等于结束日期，并保留清晰的单日工件标识。
- Export 模块明确说明：日期参数用于导出器取得数据后的本地过滤；一次 CLI 调用仍会产生一次分类查询和每个选中分类的一次或多次分页请求。范围天数不构成拆分导出的理由。
- 命令规则示例同时覆盖单日和连续日期范围，避免规则文档继续只展示开始日期与结束日期相同的调用。规则仍按既有命令前缀控制，不因本功能扩大可执行命令范围。
- 导出器在解析参数和凭据后、首次 HTTP 请求前申请固定的本机非阻塞导出锁。锁覆盖分类查询、分页、日期过滤和输出写入的完整导出生命周期，并在所有退出路径释放。
- 已有进程持有导出锁时，新进程以非零状态退出，且不得调用欧路 API。错误信息必须说明已有导出正在运行、禁止并发重试，并给出使用单次日期范围导出的方向。
- 单实例锁只限制本机 `eudic-to-anki` 导出进程，不实现跨设备或分布式锁。固定锁标识必须由两个全局 Skill 安装位置和项目工作区共同使用，避免不同入口绕过保护。
- 所有欧路 API 请求通过一个进程内请求节流器。默认上限为每分钟 25 次，相邻请求开始时间至少间隔 2.4 秒；等待使用单调时钟计算，避免系统时间调整影响节流。
- 节流器覆盖分类请求、单词分页请求以及限频后的唯一一次重试。首次请求可以立即发送，后续请求在必要时等待；不同调用者不得绕过统一请求入口。
- `429` 始终按限频处理。`403` 仅在结构化响应消息或可读响应正文明确表示访问频率过高时按限频处理；其他 `403` 继续返回认证或权限错误，不等待、不重试。
- 只有限频响应提供有效的 `Retry-After` 时才允许重试。支持非负秒数和可解析的 HTTP 日期，换算后的实际等待时间必须处于 0～120 秒。等待同时服从 `Retry-After` 和本地节流间隔，当前请求最多重试一次。没有有效等待时间、等待超过上限或重试再次失败时终止整次导出。
- 任意限频、认证、网络或解析错误发生后，不再处理剩余分类和分页。结果先写入目标目录中的临时文件，写入和关闭成功后再原子替换最终输出；失败时删除临时文件，不得新建部分结果，也不得覆盖已有的完整输出。
- 导出器维护分类请求、单词分页请求、重试请求和总请求四项统计。成功摘要和错误摘要均可显示统计，但不得记录认证头、token、完整请求对象或其他敏感数据。
- 现有分类选择、分页兼容、日期过滤、时区解析、CSV／JSON 字段、重复遇见保留和下游数据合同保持不变。
- agent 收到限频或并发保护错误后必须停止本次流程，不继续生成占位、coach、音频或 Anki 导入，也不得自动切换为逐日导出或启动新的导出进程。
- 项目文档、全局 Skill 安装说明和运行规则需要同步更新。实现完成并校验后，再用项目版本替换两个全局 Skill 副本，避免运行时命中旧指令。

## Testing Decisions

- 测试只断言外部可观察行为，包括 agent 最终生成的命令数量与参数、HTTP 调用顺序与数量、并发进程的退出结果、等待行为、输出文件是否生成及错误摘要。不得锁定私有辅助函数名称或内部数据结构。
- 第一条最高层测试接缝是 Skill 行为验收：输入「导出过去一周」「导出最近 7 天」和明确起止日期，观察最终工具调用。每种输入都必须只出现一次导出命令，并同时包含正确的开始日期、结束日期和区间输出标识。
- Skill 行为验收同时覆盖反例：不得出现 7 个单日命令，不得通过并行工具调用、子 agent 或多个输出文件间接拆分日期范围。
- 第二条最高层测试接缝是导出 CLI 的 HTTP 边界。通过替换欧路 HTTP 调用、时钟和锁实现，从一次完整 CLI 执行进入，验证分类查询、逐分类分页、节流、错误终止、统计和输出文件行为。
- 沿用项目现有 `unittest`、临时目录和 Fake Client 风格。导出测试应使用假 HTTP 响应，不访问真实欧路 API，不读取真实 token，也不依赖系统网络速度。
- 增加单次区间导出验收：多个日期只影响本地过滤边界，不增加按日重复的分类请求；每个选中分类只执行自身需要的分页请求。
- 增加请求放大回归：在 4 个分类且每类一页的固定输入下，一次导出产生 5 次基础 HTTP 请求；日期范围不得把该请求集合重复 7 次。
- 增加单实例验收：第一个导出持有锁时启动第二个导出，第二个在任何 HTTP 调用前以非零状态退出；第一个结束后，新的导出可以正常取得锁。
- 增加锁释放验收：正常完成、API 错误、输出错误和未处理异常路径均释放锁，不留下永久阻塞后续任务的状态。
- 增加节流验收：使用假单调时钟记录每次请求开始时间，除首次请求外，相邻请求间隔不得少于 2.4 秒；测试本身不执行真实等待。
- 增加统一入口验收：分类请求、分页请求和限频重试都计入节流与统计，不允许其中任一请求类型绕过。
- 增加 `429` 验收：提供有效 `Retry-After` 时只重试当前请求一次；第二次成功后继续流程，第二次失败后停止后续请求。
- 增加限频 `403` 验收：响应正文明确表示访问频率过高时，行为与限频合同一致。
- 增加普通 `403` 验收：认证失败或权限错误不等待、不重试，直接返回明确错误并停止后续请求。
- 增加无效等待信息验收：缺少 `Retry-After`、无法解析、负数或换算后超过 120 秒时不猜测或截断等待时长，直接终止导出。
- 增加失败原子性验收：任意分类或分页失败时不生成新的最终 CSV／JSON；如果目标路径已有旧文件，不得用部分结果覆盖。
- 增加统计验收：成功和失败摘要中的分类请求数、分页请求数、重试请求数与总请求数准确，且日志中不出现 token 或认证头。
- 增加兼容性验收：单日、指定分类、全部分类、CSV、JSON、页码从 1 或 0 开始的兼容逻辑，以及本地时区日期边界保持原有结果。
- 默认回归继续运行完整 `unittest` 测试集和 Skill 校验。真实欧路 API 冒烟测试不进入默认自动化测试，避免消耗配额或再次触发限频。

## Out of Scope

- 不修改欧路服务端访问限制，也不保证其他客户端或其他设备产生的请求不会占用同一账号配额。
- 不实现跨设备、分布式或云端导出锁。
- 不把连续日期范围拆分为逐日缓存任务，也不建立后台任务队列。
- 不引入常驻导出守护进程或新的图形界面。
- 不假设欧路 API 支持服务端日期过滤；没有经过官方接口确认前，不新增未验证的日期查询参数。
- 不在本规格中实现完整生词缓存、增量同步或分类结果的长期缓存。
- 不改变欧路 token 的配置方式、分类选择规则、分页数据格式或本地时区语义。
- 不调整 coach 生成、词汇分类、Edge-TTS、Anki note、卡片模板、牌组迁移或同步行为。
- 不对普通认证 `403` 进行自动登录、token 刷新或无限重试。
- 不在默认自动化测试中调用真实欧路 API。
- 不在本规格阶段修改代码、更新全局 Skill 或执行真实生词导出。
- 不把本规格发布到 GitHub Issue；本次交付只保存为项目内本地文档。

## Further Notes

- 本次故障的直接触发是 agent 把一个 7 天闭区间并行展开为 7 次导出。导出器本身接受开始日期和结束日期，不需要逐日调用。
- 诊断使用假 HTTP 边界复现了请求放大：4 个分类、每类一页时，单次区间导出需要 5 次基础请求；7 次单日导出会放大为 35 次请求。该结果解释了为什么错误规划会迅速越过故障现场显示的每分钟 30 次限制。
- 每分钟 25 次是基于故障现场配额设置的本地安全值，为网络抖动、其他客户端请求和服务端计时边界保留余量。实现时不得把该值提高到服务上限后再依赖精确时间边界。
- 单实例锁用于阻止本机并发放大，请求节流用于控制单个正常导出的请求速度。两者解决不同问题，均需要实施。
- 日期范围工作流已经具备正确的单次命令，主要文档问题是主 Skill 没有强制路由到该工作流，且主流程和 Export 模块继续展示单日命令。实施时应消除重复指令源，避免后续文档再次漂移。
- 实施顺序建议为：先增加 Skill 路由和范围行为验收，再实现导出锁与请求节流，随后补充限频错误处理和请求统计，最后更新规则、模块文档并同步全局 Skill。
